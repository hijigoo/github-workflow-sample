## 실습 목표와 범위

GitHub Enterprise Cloud(GHEC)의 Enterprise Managed Users(EMU) 환경에서
Copilot에게 프로젝트를 질문하고, 완료 조건이 있는 업무를 요청한 뒤 결과를 검수합니다.
대상은 PM과 업무 담당자이며, 직접 코드를 작성하는 능력보다 근거를 확인하는 과정을 연습합니다.

원본 저장소를 포크하지 않습니다. 코드를 clone한 뒤 EMU 조직의 신규 저장소에 등록합니다.
기존 기록을 복원하는 대신 실습 저장소에서 Issue, PR, 검사 결과를 새로 만듭니다.

* 프로젝트의 현재 기능과 확인되지 않은 사항 구분
* 기능 이슈 생성과 Copilot 코딩 에이전트 할당
* 요구사항을 기준으로 PR 검수와 보완 요청
* 보안 결과 해석과 미해결 항목의 후속 조치 요청

자동 병합, Pages 게시, QA·운영 배포, 환경 승인은 필수 범위에서 제외합니다.
배포나 병합은 강사와 저장소 담당자가 별도로 결정합니다.

> [!WARNING]
> 아래의 'runner 과금 대상' 표시는 EMU 조직의 private/internal 저장소에서
> GitHub-hosted runner를 실행해 과금 대상 사용량이 발생하는 활동입니다.
> 월 포함량 안에서는 추가 청구가 없을 수 있으며, 초과분은 조직·기업의 청구 설정에 따라 과금됩니다.
> 실패한 실행·재실행도 사용량에 포함됩니다. 수업 전에 잔여 포함량과 예산·차단 설정을 확인합니다.
> Copilot AI 사용량과 아티팩트 저장 비용은 runner 사용량과 별도로 확인합니다.

> [!IMPORTANT]
> [README](../README.md), [기존 열람 가이드](reading-guide.md),
> [기존 요구사항](requirements/v1.1.0.md)은 원본의 기록 열람 시나리오를 설명합니다.
> 이 핸즈온은 별도의 능동형 실습입니다. 원본 PR 번호, 공개 사이트, 릴리스,
> 보안 스냅샷을 신규 저장소에서 생성된 결과로 사용하지 않습니다.

## 실습 사전 준비

<details>
<summary>사전 준비 내용 펼치기</summary>

수업 시간과 별도로 준비합니다. 개인별 또는 조별 저장소에서 전체 흐름을 한 번 실행해 봅니다.

### 신규 저장소에 코드 등록

1. EMU 조직에 빈 저장소를 만듭니다. EMU 조직에서는 공개(public) 저장소를 만들 수 없으므로
   조직 정책에 따라 비공개(private) 또는 내부 공개(internal)를 선택합니다.
2. 원본 코드를 clone합니다. Git 이력을 유지하더라도 과거 브랜치를 모두 옮길 필요는 없습니다.
3. 로컬 저장소의 원격 대상을 신규 저장소로 설정하고, 주소를 확인한 뒤 코드를 등록합니다.
4. 실습의 기준 브랜치를 `main`으로 설정합니다.
5. 수강자가 원본이 아닌 신규 저장소를 열고 있는지 확인합니다.

Git 코드와 이력을 옮겨도 Issue, PR, 리뷰, Actions 실행, 보안 경고, 환경 승인,
저장소 설정은 이전되지 않습니다. 새 저장소의 번호와 실행 링크를 사용합니다.
원본 저장소를 수정하거나 실습 결과를 원본으로 보내지 않습니다.
개인 소유가 아닌 조직 소유 저장소를 사용합니다. EMU 개인 저장소에서는
GitHub-hosted runner와 Copilot 코딩 에이전트를 사용할 수 없습니다.

### 계정과 자동화 점검

* [ ] 실습 계정의 조직 가입과 저장소 접근·이슈 생성·PR 댓글 작성 권한을 확인했습니다.
* [ ] 브라우저와 VS Code에서 사용할 계정 및 해당 계정의 Copilot 좌석을 확인했습니다.
* [ ] 조직과 저장소에서 코딩 에이전트 사용을 허용하는지 확인했습니다.
* [ ] 이슈 생성·Copilot 할당부터 작업 시작과 PR 생성까지 시험했습니다.
* [ ] Actions 실행 환경과 workflow 실행 승인 담당자를 확인했습니다.

VS Code의 Copilot Chat 접근 권한과 GitHub의 코딩 에이전트 할당 권한은 별개입니다.
사용하는 클라이언트가 할당 작업을 지원하지 않으면 GitHub의 이슈 담당자 선택에서
Copilot을 직접 선택합니다. 선택 자체가 불가능하면 강사에게 알리고 실행 실습을 보류합니다.

[Build and Test](../.github/workflows/ci.yml)에서 의존성 설치,
`npm run typecheck`, `npm test`, `npm run build` 결과를 확인합니다.
원본 CI는 Node.js 24와 별도의 npm 패키지 소스를 사용합니다.
조직에서 허용한 소스로 설치할 수 있는지 확인하고, 실패를 정상 검증으로 표시하지 않습니다.
현재 CI와 CodeQL workflow는 `ubuntu-latest`를 사용합니다.
GitHub-hosted runner 사용 정책과 Actions 실행 예산을 확인합니다.
질문·이슈 작성·기록 열람 자체에는 runner가 필요하지 않지만,
코딩 에이전트의 작업과 CI·CodeQL 실행에는 실행 환경이 필요합니다.

CI와 Copilot 실행 환경에서 의존성과 Playwright 브라우저를 설치할 수 있는지 미리 확인합니다.
접근이 막히면 관리자에게 허용된 패키지 소스와 네트워크 설정을 확인합니다.

[샘플 PR 작성 workflow](../.github/workflows/sample-records.yml)는 원본 저장소에만
쓰기 작업을 허용합니다. 신규 저장소의 PR 준비 도구로 사용하지 않습니다.
릴리스·운영 workflow도 별도 설정 없이 실행하지 않습니다.

### Copilot PR의 workflow 실행 승인

Copilot이 PR에 변경을 올린 뒤에도 기본적으로 Actions workflow가 자동 실행되지 않고
사람의 승인을 기다릴 수 있습니다. PR 초안이나 에이전트 작업 완료가 CI 완료를 뜻하지 않습니다.

1. 저장소 쓰기 권한과 조직 정책상 승인 권한이 있는 사람이 PR 변경 내용을 검토합니다.
2. 코드와 함께 workflow 변경, 설치 스크립트, 외부 통신·비밀정보 접근 가능성을 확인합니다.
3. 안전하게 실행할 수 있다고 판단한 경우 PR의 `Approve and run workflows`를 선택합니다.
4. PR의 Checks와 저장소 Actions에서 대상 커밋의 실행 링크와 결과를 확인합니다.
5. 후속 커밋으로 승인이 다시 필요하면 같은 검토를 반복합니다.

PR 리뷰 승인, workflow 실행 승인, 환경 배포 승인은 서로 다릅니다.
이번 필수 실습에서는 환경 배포 승인을 진행하지 않습니다.

### 검수용 Issue와 PR 준비

에이전트 실행을 기다리지 않고 검수할 수 있도록 신규 저장소에 완료 조건이 명확한
Issue와 열린 PR을 하나 준비합니다. 수강자가 요청할 제목 검색과 겹치지 않는
작성일 정렬 등을 사용하고, Copilot에게 구현을 요청해 준비할 수 있습니다.

예를 들어 최신순·오래된순 선택, 상태·기간 검색과 동시 적용,
최초 조회와 초기화 시 기본 정렬인 최신순(작성일 내림차순) 적용을 완료 조건으로 정합니다.
PR 본문은 [PR 템플릿](../.github/PULL_REQUEST_TEMPLATE)을 사용하고
관련 이슈와 실행한 테스트·결과를 기록합니다. 이슈와 PR 링크를 수강자에게 제공합니다.

검수는 완료 조건을 실제로 충족하는지 확인하는 활동입니다.
일부러 결함을 만들 필요는 없으며, 누락이 있을 때만 보완을 요청합니다.

### 신규 보안 결과 준비

사용할 보안 기능의 이용 권한·비용과 신규 저장소의 활성화 여부를 관리자에게 확인합니다.
의존성 그래프·Dependabot alerts, Code scanning, Secret scanning은 별도로 확인하고,
기본 브랜치에서 실제 결과를 확보합니다.

* Dependabot은 의존성 경고를, Code scanning은 분석 도구가 발견한 코드 문제를 확인하는 데 사용합니다.
* [CodeQL workflow](../.github/workflows/codeql.yml)를 사용할 때는 중복 분석 설정과 실행 권한을 확인합니다.
* 수업에서 사용할 미해결 경고 한 건의 도구, 대상, 상태, 확인 시각, 신규 저장소 링크를 확보합니다.
* 경고를 열람할 수 없는 수강자에게는 강사가 확인한 비식별 요약을 제공합니다.

[기존 보안 리포트](security-report.md)와 [보안 스냅샷](security/evidence/security-snapshot.json)은
원본의 과거 상태입니다. 코드를 가져오면 같은 경고 번호나 상태가 재현된다고 가정하지 않습니다.
이미 수정된 코드를 취약하게 되돌려 경고를 만들지 않습니다.

관찰용 `lodash@4.17.20`은 비배포 교육 환경에서 조직이 허용한 경우에만 사용합니다.
실제 신규 검사 결과를 확보하지 못하면 샘플 보고서 해석과 검사 설정 요청으로 대체합니다.
원본에는 패키지 소스 접근 차단 기록이 있으므로 업데이트 작업의 네트워크 접근도 미리 확인합니다.
인증 정보 추가, TLS 검증 해제, 잠금 파일 무결성 값 변조로 우회하지 않습니다.

Secret scanning은 선택 시연으로 둡니다. 실제 키·토큰·비밀번호를 넣지 않으며,
정책이 허용하는 안전한 시험 데이터만 사용합니다. 탐지를 위해 보호 기능을 해제하지 않습니다.

## 수강자 시작 확인

* [ ] EMU 계정으로 로그인하고 강사가 제공한 신규 저장소를 열었습니다.
* [ ] 실습 조직 가입, 저장소 역할, 현재 계정의 Copilot 좌석을 확인했습니다.
* [ ] 질문에 사용할 Copilot과 이슈·PR 작업 권한을 확인했습니다.
* [ ] 강사가 준비한 검수용 PR과 보안 결과 또는 대체 자료의 링크를 받았습니다.
* [ ] 원본 기록과 신규 저장소 기록을 구분할 수 있습니다.

요청 예시의 `조직/저장소`, `이슈 번호`, `PR 링크`는 실제 실습 대상 값으로 바꿉니다.
GitHub 웹에서는 선택한 저장소를, VS Code에서는 현재 연 폴더와 연결된 원격 저장소를 확인합니다.
PR이나 보안 결과를 질문할 때는 해당 대상의 링크도 명시합니다.
Copilot의 답변만으로 작업 완료를 판단하지 않고 GitHub 화면과 실행 결과를 함께 확인합니다.

## [실습 1] 프로젝트 이해하기 (예상 소요시간 15분)

> [!NOTE]
> runner 실행 없음: 질문과 코드·문서 열람만 진행합니다.

먼저 GitHub 웹의 저장소 선택 또는 VS Code에서 연 폴더가 신규 저장소인지 확인합니다.
웹은 GitHub에 올라온 코드, 로컬 작업은 열린 폴더의 파일이 출발점이므로
로컬 변경이 아직 GitHub에 반영되지 않았다면 답변의 근거가 다를 수 있습니다.
그다음 코드와 문서를 근거로 현재 기능을 파악합니다.

```text
현재 실습 대상은 조직/저장소야.
이 프로젝트는 누가 사용하고 어떤 문제를 해결하는지 설명해줘.
주요 기능과 관련 코드·테스트의 위치를 알려줘.
실제 구현으로 확인한 내용과 문서에만 있는 내용을 구분해줘.
지금은 코드를 바꾸거나 이슈를 만들지 마.
```

추가로 궁금한 점을 자유롭게 질문합니다.

```text
상태와 기간을 동시에 적용하면 어떻게 동작해?
잘못된 기간을 입력하면 이전 조회 결과는 어떻게 돼?
실제 서버나 데이터베이스를 쓰는 부분과 교육용 격리 코드를 구분해줘.
문서에 연결된 원본 PR과 보안 기록을 이 실습 저장소의 기록으로 해석하지 마.
접근하거나 확인하지 못한 내용은 확인 불가라고 표시해줘.
```

완료 기준은 현재 기능 세 가지와 확인되지 않은 사항 한 가지를 자신의 말로 설명하는 것입니다.
답변의 파일 링크를 열어 실제 근거와 맞는지 확인합니다.

## [실습 2] 기능 이슈 생성과 Copilot 할당 (예상 소요시간 20분)

> [!WARNING]
> runner 과금 대상: Copilot이 GitHub Actions 기반 환경에서 구현·테스트하거나
> 생성된 PR에서 CI·CodeQL이 실행될 때 사용량이 발생합니다.
> 이슈 초안 작성·등록·할당만으로 runner가 실행된 것은 아니며, 실제 작업 시작 여부를 확인합니다.

문의 제목 검색처럼 작은 기능 하나를 요청합니다.
먼저 초안을 받고, 사람이 범위와 완료 조건을 확인한 뒤 등록과 할당을 진행합니다.

```text
조직/저장소에 문의 제목 검색을 추가하고 싶어.
현재 코드와 열린 이슈·PR을 확인해 중복 구현이나 중복 요청을 피하고,
아래 완료 조건을 포함한 이슈 초안을 작성해줘.
아직 이슈를 등록하거나 Copilot에게 할당하거나 구현하지 마.

1. 문의 제목 일부로 검색할 수 있다.
2. 제목 검색과 기존 상태·기간 조건을 동시에 적용한다.
3. 검색 결과가 없으면 빈 결과를 안내한다.
4. 초기화하면 검색어도 지워지고 전체 조회로 돌아간다.
5. 기존 기간 오류 처리와 조회 기능을 유지하고 관련 테스트를 추가한다.

가상 데이터만 사용하고 서버·DB·배포 기능은 추가하지 마.
자동 병합하거나 배포하지 마.
```

초안에서 요청하지 않은 기능이 추가되지 않았는지, 기존 동작 유지와 테스트 기준이
포함됐는지 확인하고 필요한 내용을 수정합니다. 확인이 끝나면 등록을 요청합니다.

```text
검토한 초안으로 조직/저장소에 이슈를 등록하고 링크를 알려줘.
아직 Copilot에게 할당하지 마. 등록 기능을 사용할 수 없으면 제출할 제목과 본문을 알려줘.
```

GitHub에서 직접 제출하는 방법도 가능합니다. 실제 이슈가 등록된 것을 확인한 뒤 할당합니다.

```text
조직/저장소의 이슈 번호를 Copilot에게 할당하고 작업 상태를 알려줘.
할당에 실패하면 이슈를 다시 만들지 말고 실패 이유를 알려줘.
자동 병합하거나 배포하지 마.
```

담당자와 실제 작업 시작 여부를 각각 확인하고 이슈 링크를 보관합니다.
초안 작성, 이슈 등록, 에이전트 할당은 서로 다른 단계이며 초안만으로 작업이 시작되지 않습니다.

PR이 생겼지만 Checks가 시작되지 않았다면 승인 대기 여부를 먼저 확인합니다.
권한 있는 검토자가 변경 내용을 확인한 뒤 실행을 승인하고 해당 커밋의 결과를 확인합니다.
승인 대기는 테스트 실패나 구현 실패와 다르게 기록합니다.

이미 같은 기능이 있다면 강사와 겹치지 않는 작은 요청으로 바꿉니다.
완료 기준은 중복되지 않는 이슈, Copilot 할당, 작업 시작의 확인입니다.
이 단계에서 PR 생성이나 구현 완료까지 보장되는 것은 아닙니다.

## [실습 3] 준비된 PR 검수와 후속 요청 (예상 소요시간 25분)

> [!WARNING]
> 조건부 runner 과금 대상: 기존 diff·검사 결과 열람과 댓글 작성에는 runner가 필요하지 않습니다.
> 보완 요청이나 추가 개선 할당으로 Actions 기반 에이전트 작업 또는 CI·CodeQL이 새로 실행되면
> 사용량이 발생합니다.

강사가 준비한 PR을 사용합니다. 아래는 작성일 정렬 PR의 예시이며,
다른 기능을 준비했다면 해당 완료 조건으로 바꿉니다.
GitHub PR 화면에서 Copilot을 열 수 있다면 해당 PR이 질문 맥락에 포함됐는지 확인합니다.
지원하지 않는 환경에서는 사용하는 Chat에 저장소와 PR 링크를 직접 지정합니다.
Files changed에서 파일별 질문 기능을 사용할 수 있다면 변경 파일 하나에 대해서도 질문해 봅니다.

```text
조직/저장소의 PR 링크를 연결된 이슈의 완료 조건과 대조해줘.
각 조건을 충족·미충족·확인 불가로 구분하고 코드·테스트 근거를 제시해줘.
조건별로 구현 위치, 테스트 위치, 실행 결과를 연결해줘.
변경 diff뿐 아니라 기존 코드와 테스트도 확인하고,
구현 누락, 테스트 누락, 근거를 찾지 못한 경우를 구분해줘.
실행한 테스트와 결과, 실행하지 못한 확인을 구분해줘.
최초 조회가 기본 정렬인 최신순(작성일 내림차순)인지,
오래된순으로 변경한 뒤 초기화하면 최신순으로 돌아오는지 확인해줘.
선택창 표시만 아니라 실제 목록 순서도 확인해줘.
정상·예외·기존 동작에서 각각 한 가지 이상 검증 근거를 찾아줘.
새 테스트를 위해 기존 회귀 시나리오를 삭제하거나 대체하지 않았는지도 확인해줘.
테스트 통과나 PR 본문의 완료 표시만으로 충족이라고 판단하지 마.
지금은 검수 결과만 알려주고 파일이나 GitHub 기록을 변경하지 마.
```

구현이 있어도 테스트 근거는 없을 수 있습니다. 반대로 diff에 테스트가 안 보여도
기존 테스트에서 검증할 수 있으므로, 발췌만 보고 누락을 단정하지 않습니다.
본문의 테스트 통과 설명은 실행 환경·대상 커밋·원본 결과와 대조합니다.
CI가 성공했어도 테스트에 없는 초기화 동작까지 보장하지는 않습니다.
제목 검색으로 빈 결과를 만드는 UI 테스트는 기존 기간 조건의 빈 결과 테스트를 대체하지 않습니다.
두 시나리오를 모두 유지하고, 단위 테스트만 있다면 기능 결함과 구분해 UI 회귀 검증 보완으로 기록합니다.

답변의 근거를 확인한 뒤 원래 요구사항의 누락은 같은 PR에서 보완 요청합니다.

```text
확인한 원래 요구사항의 누락을 이 PR에 보완 요청 댓글로 남겨줘.
재현 절차, 기대 결과, 실제 결과, 필요한 회귀 테스트를 포함해줘.
같은 누락으로 새 이슈를 중복 생성하지 마.
```

Copilot이 작성한 PR이라면 조직에서 지원하는 방식으로 Copilot에게 보완을 요청합니다.
댓글 게시 성공과 에이전트의 후속 작업 시작은 별도로 확인합니다.
사람이 작성한 준비용 PR에는 댓글만 남기고, 실행 주체는 강사가 안내합니다.
보완 댓글을 남긴 뒤에는 새 수정 커밋과 검사 결과가 생겼는지 확인합니다.
사람이 작성한 PR에 댓글을 남겼다는 이유만으로 Copilot이 자동 수정한다고 판단하지 않습니다.

검수 중 발견한 새로운 요구사항은 원래 PR에 섞지 않고 별도 이슈로 만듭니다.
연습 예시는 강사가 중복 여부를 확인한 뒤 사용합니다.

```text
키보드만으로 정렬 선택과 조회를 사용할 수 있는지 먼저 확인해줘.
기존 요구사항·구현·열린 이슈에 없는 추가 개선이 필요할 때만,
완료 조건이 있는 별도 이슈 초안을 작성해줘.
이미 지원하거나 기존 요청에 포함돼 있으면 새 이슈를 만들지 마.
아직 이슈를 등록하거나 Copilot에게 할당하거나 구현하지 마.
```

초안을 사람이 검토한 뒤 등록하고, 실제 이슈를 확인한 다음 할당합니다.

```text
검토한 추가 개선 초안으로 조직/저장소에 이슈를 등록하고 링크를 알려줘.
아직 Copilot에게 할당하지 마. 등록 기능을 사용할 수 없으면 제출할 제목과 본문을 알려줘.
```

```text
조직/저장소의 등록된 추가 개선 이슈 번호를 Copilot에게 할당하고 작업 상태를 알려줘.
할당에 실패하면 이슈를 다시 만들지 말고 실패 이유를 알려줘.
자동 병합하거나 배포하지 마.
```

완료 기준은 조건별 충족·미충족·확인 불가 판정과 근거가 남는 것입니다.
누락이 있으면 보완 댓글을 남기고, 새 요구사항이 없다면 추가 이슈를 억지로 만들지 않습니다.

## [실습 4] 보안 결과 해석과 조치 요청 (예상 소요시간 20분)

> [!WARNING]
> 조건부 runner 과금 대상: 기존 보안 결과 열람·이슈 작성만으로는 runner가 필요하지 않습니다.
> Actions 기반 에이전트의 수정 작업, CI 실행, CodeQL 분석·재실행에는 사용량이 발생합니다.
> Dependabot·Secret scanning 결과 조회를 CodeQL runner 실행과 혼동하지 않습니다.

신규 저장소의 현재 결과를 먼저 확인합니다.

```text
조직/저장소의 현재 보안 경고를 쉽게 설명해줘.
도구, 대상, 상태, 확인 시점, 영향 범위, 권장 조치를 구분해줘.
원본 저장소의 security-report.md와 스냅샷은 과거 참고자료로만 사용해줘.
접근 권한이 없어 조회하지 못한 결과를 현재 경고로 단정하지 마.
경고 번호는 도구와 저장소를 함께 표시하고 민감 값은 출력하지 마.
아직 이슈를 만들거나 코드를 변경하지 마.
```

탐지된 사실과 실제 영향은 구분합니다. 실제 결과를 읽을 때는 다음을 함께 확인합니다.

* Dependabot: 취약 버전 포함과 실제 악용 가능성은 별도입니다. 직접·간접 의존성,
  설치 버전과 수정 버전, 사용 경로를 확인합니다. 개발 의존성이라는 이유만으로 무해하다고 보지 않습니다.
* Code scanning: 경고 위치의 입력 흐름, 서버 실행·외부 접근·배포 포함 여부를 확인합니다.
  비배포 격리 코드의 경고를 공개 화면의 취약점으로 단정하거나 교육용이라는 이유만으로 오탐 처리하지 않습니다.
* Secret scanning: 현재 파일뿐 아니라 과거 커밋에서도 탐지될 수 있습니다.
  시험용 파일명만으로 안전을 확정하지 않으며 미발급 증빙이 실제 탐지 대상과 일치하는지 확인합니다.
  유효성 `unknown`은 무효라는 증거가 아니고, 공개 유출 표시는 별도 확인 대상입니다.

강사가 제공한 실제 결과와 설명을 대조하고, 먼저 조사와 수정 중 필요한 일을 판단합니다.

```text
확인한 경고 한 건에 대해 탐지된 사실, 실제 영향 판단, 확인하지 못한 사항을 분리해줘.
현재 근거로 수정이 필요한지 판단할 수 있어?
부족하면 먼저 조사할 내용을, 수정이 필요하면 수정 범위를 이슈 초안으로 정리해줘.
경고 원본 링크와 확인 기준을 포함하고 기존 이슈·PR과 중복되지 않게 해줘.
아직 이슈를 등록하거나 Copilot에게 할당하지 마.
```

사람이 초안을 검토하고 등록합니다. 영향이나 수정 필요성이 미확인이면 조사 이슈로 남기고
담당자를 정합니다. 코드·테스트 수정이 필요하다고 확인된 경우에만 다음 완료 조건을 담아
Copilot에게 할당합니다. 등록과 할당은 실습 2와 같은 방식으로 나눠 진행합니다.

```text
수정이 필요하다고 확인한 조치 이슈에 다음 완료 조건이 있는지 확인한 뒤
조직/저장소의 이슈 번호를 Copilot에게 할당해줘.

1. 원인에 맞는 수정이나 의존성 업데이트를 한다.
2. 관련 테스트와 빌드 결과를 제시한다.
3. 대상 브랜치와 커밋을 명시하고 해당 보안 도구의 재검사 결과를 확인한다.
4. PR에서 가능한 확인과 기본 브랜치 반영 후 필요한 확인을 구분한다.
5. 의존성 변경은 잠금 파일의 설치 버전·다운로드 출처를 확인하고 관련 경고를 각각 추적한다.

실제 비밀정보나 원시 토큰을 이슈에 복사하지 마.
검사 실패, 접근 차단, 확인 대기는 해결 완료로 표시하지 마.
자동 병합하거나 배포하지 마.
```

Dependabot 경고를 CodeQL 성공으로 해결됐다고 판단하지 않습니다.
한 패키지의 업데이트로 다른 코드 경고까지 해결된다고 보지 않으며,
이슈와 PR 본문의 도구명도 실제 조치 대상과 맞는지 확인합니다.
Dependabot 의존성 조치를 Code scanning 조치로 기록했다면 본문도 정정합니다.
Code scanning의 Fixed, 근거를 남긴 Dismissed, 시험 데이터의 Resolved도 같은 의미가 아닙니다.
실제 중요정보가 발견되면 공개 이슈로 옮기지 않고 조직의 사고 대응 절차를 따릅니다.
파일 삭제나 PR 병합만으로 키 회수·교체가 완료되지는 않습니다.

검사가 불가능하면 강사의 비식별 보고서로 해석만 연습합니다.
후속 이슈는 실제 취약점 수정 대신 검사 활성화·권한·패키지 소스 접근 확인 요청으로 작성합니다.
관리자 작업이 필요한 설정은 Copilot에게 할당해도 자동으로 해결되지 않으므로 담당자를 명시합니다.

완료 기준은 현재 결과에 근거한 조사·조치 이슈와 필요한 담당자 지정입니다.
조사만 필요한 상황에서 구현이나 PR 생성을 억지로 요청하지 않습니다.
보고서만 사용했다면 실제 경고 해소를 검증한 것으로 기록하지 않습니다.

## [실습 5] 내가 요청한 결과 확인 (예상 소요시간 10분)

> [!WARNING]
> 조건부 runner 과금 대상: 기존 PR·Checks·Actions 결과 열람에는 runner가 필요하지 않습니다.
> workflow 실행을 승인해 검사가 시작되거나 실패한 검사를 재실행하면 사용량이 발생합니다.
> 실습 2·4에서 이미 실행한 결과를 다시 읽는 것은 새 runner 실행이 아닙니다.

실습 2의 이슈로 돌아와 연결된 PR과 작업 상태를 확인합니다.

```text
조직/저장소의 이슈 번호에 연결된 Copilot 작업과 PR 상태를 확인해줘.
원래 완료 조건별로 구현·검증 근거와 미충족·확인 불가 사항을 정리해줘.
PR 상태와 최신 커밋을 확인하고, 에이전트 작업 완료와 해당 커밋의 저장소 CI 결과를 구분해줘.
정상·예외·기존 동작의 테스트가 유지됐는지와 요청에 없던 동작 변경도 확인해줘.
PR이 없거나 작업 중이면 현재 상태와 남은 확인을 알려줘.
PR 생성, 테스트 통과, 보안 경고 해소, 병합, 배포를 서로 구분해줘.
자동 병합하거나 배포하지 마.
```

에이전트 실행 성공은 저장소 CI 성공이나 요구사항 충족을 뜻하지 않습니다.
PR이 초안인지, CI가 승인 대기인지, 어떤 커밋을 검사했는지 각각 확인합니다.
제목 검색에 공백 제거·대소문자 무시 등이 추가됐다면 의도한 동작인지와 검증 근거도 확인합니다.

PR이 준비됐다면 요청한 제목 검색 기능을 검수합니다.
지연되면 준비된 PR로 검수 실습을 마치고, 본인 PR 확인은 후속 과제로 남깁니다.
보안 수정 PR도 같은 방식으로 검수하되 해당 도구의 재검사 결과를 별도로 확인합니다.
의존성 업데이트에서는 버전뿐 아니라 잠금 파일의 다운로드 출처가 승인된 소스인지 확인합니다.
공식 npm으로 바뀌었더라도 조직이 승인한 출처라고 단정하지 않습니다.
승인 근거가 없으면 정책 담당자의 확인 대기로 남기며, 임의로 기존 소스로 되돌려 우회하지 않습니다.
같은 패키지의 경고가 여러 개면 각각의 수정 버전과 후속 상태를 대조합니다.
기본 브랜치에 아직 반영되지 않은 수정 PR만으로 경고 해소를 선언하지 않으며,
기본 브랜치의 Open 상태만으로 수정 후보가 실패했다고 단정하지도 않습니다.
CI가 실행 승인 대기라면 검토·승인 후 PR의 Checks와 Actions에서 결과를 확인합니다.
수업 안에 승인이나 실행을 마치지 못하면 검증 대기로 기록하고 후속 담당자를 정합니다.

## 실습 결과 기록

수업 마지막에 다음 항목을 실습 이슈 또는 강사가 지정한 제출 위치에 남깁니다.
별도 파일을 만들 필요는 없습니다.

* 완료한 활동: 프로젝트에서 이해한 내용, 생성한 이슈·PR, 진행한 검수의 링크
* 확인된 결과: 완료 조건별 판정과 테스트·보안 결과의 근거, 대체 자료 사용 여부
* 남은 일: 승인 대기·미검증 항목과 후속 확인 담당자

실습 활동 완료와 구현·검증 완료를 구분합니다. 준비된 PR로 검수 활동을 마쳤더라도
본인 PR의 CI가 승인 대기라면 검증 대기로 기록하고, 최종 검수는 후속 과제로 남깁니다.

## 문제가 생겼을 때

### Copilot 할당 또는 작업 시작이 안 됨

신규 저장소 접근 권한, 현재 로그인 계정의 Copilot 좌석과 코딩 에이전트 허용 여부를 확인합니다.
클라이언트의 할당 기능만 없다면 GitHub 화면에서 할당합니다.
권한이나 정책이 막혀 있으면 관리자에게 요청하고 강사의 준비용 PR로 검수를 진행합니다.
실행되지 않은 작업을 완료로 기록하지 않습니다.

### 보안 결과가 없거나 열리지 않음

기능 활성화, 열람 권한, 기본 브랜치의 최초 검사 여부와 분석 시각을 확인합니다.
경고가 없다는 이유만으로 미검사 범위까지 안전하다고 판단하지 않습니다.
실제 결과를 확보하지 못하면 비식별 자료를 사용하고 대체 실습임을 기록합니다.

### 설치나 Actions 검사가 실패함

먼저 workflow가 실행됐는지 확인합니다. Copilot PR의 실행 승인 대기라면 실패가 아니라 미실행 상태입니다.
승인 담당자가 PR 변경과 workflow를 검토한 뒤 `Approve and run workflows`로 승인하고,
PR Checks와 Actions에서 동일 커밋의 결과를 확인합니다. 배포 승인과 혼동하지 않습니다.

runner, 허용된 Actions, 패키지·브라우저 다운로드 경로와 실패 로그를 확인합니다.
네트워크 접근 차단과 코드 오류를 구분하고 권한 담당자에게 요청합니다.
검증을 끄거나 비밀정보를 공개 댓글에 붙여 우회하지 않습니다.

### 같은 이슈나 PR이 여러 번 생성됨

재요청 전에 기존 이슈와 연결된 작업을 확인합니다.
중복 기록은 강사와 정리하고, 같은 작업은 기존 이슈·PR에서 이어갑니다.
원래 요구사항의 누락과 새로운 개선 요청을 구분합니다.
